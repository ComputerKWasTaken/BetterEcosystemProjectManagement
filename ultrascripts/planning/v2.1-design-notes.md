# BetterDungeon V2.1 Investigation and Design Notes

## Purpose

These notes capture the reasoning behind the roadmap and the decisions that
still need a spike or product choice. They are not implementation truth.

## Heartbeat: Durable Discovery Is Not Live Presence

The current heartbeat is a durable Story Card written on adventure entry and
updated as BetterDungeon observes changes. That makes it good at advertising
modules, ops, and versions, but a previous device can leave a valid-looking card
behind. Timestamps and clean-exit invalidation improve diagnostics but cannot
prove liveness after a crash, network loss, tab kill, or switch to a vanilla device.

Recommended protocol:

1. Treat heartbeat as a cached capability advertisement.
2. Have the script write a liveness request with a fresh nonce and its current
   turn/action marker.
3. Have the active BetterDungeon client acknowledge that nonce with its session
   id, platform, adventure id, protocol version, and observed marker.
4. Cache the acknowledgement for a short, turn-bounded lease.
5. Expose three states: `available` after acknowledgement, `uncertain` while a
   fresh check is pending, and `unavailable` after expiry/failure.

Open choices:

- Whether Enhanced scripts may optimistically use advertised capabilities while
  uncertain. Required scripts should wait for acknowledgement.
- Exact lease duration in turns and whether wall-clock age is a secondary guard.
- Whether the liveness op belongs to core transport or a reserved SDK op. Core is
  cleaner because discovery should not depend on the optional SDK module.
- Multi-client arbitration. An acknowledgement should identify the responding
  session without assuming only one BetterDungeon client is connected.

Platform naming should use `PC` and `Mobile` as the user-facing values. Keep
transport/runtime detail in a separate field so `PC` does not become a proxy for
Chromium versus Firefox.

## Audio Module

The module is valuable, but it should be a declarative audio service rather than
an arbitrary Web Audio escape hatch.

Suggested split:

- `ultrascripts:state:audio` describes desired ambient playback and optionally
  exposes current playback/capability state.
- Ops handle short synthesized effects where acknowledgement and errors matter.
- Ambient requests use catalog track IDs, not remote URLs in V1.
- Synth requests use bounded notes, oscillator types, ADSR envelopes, duration,
  volume, and optional simple sequencing.

Questions to settle:

- Does the latest state win globally, or does each script/namespace receive a
  channel that a mixer arbitrates?
- Should leaving the adventure always stop audio, or may a track cross internal
  adventure navigation?
- How does a player permanently mute a noisy script without disabling all Audio?
- Are overlapping effects capped per script and globally?

Key pitfalls are browser autoplay rules, mobile background suspension, rapid
state churn, clipping, and cleanup. A visible global stop/mute is essential.

## JS Module

This is the highest-risk proposed module. A Web Worker improves isolation and
allows hard termination, but `eval` inside a Worker is not by itself a complete
security boundary. The implementation must ensure the worker has no privileged
extension/page references and should assume hostile code.

Recommended V1 contract:

- source string plus JSON input;
- JSON output or structured error;
- no network, storage, DOM, imports, timers, extension APIs, or cross-request globals;
- strict source/input/output limits;
- worker termination on wall-clock timeout;
- one-shot workers initially to eliminate state leakage;
- fixed engine version and no promise of bypassing every AI Dungeon limit.

Before coding, write an escape/abuse suite covering constructor chains, dynamic
code creation, prototype mutation, infinite loops, allocation bombs, oversized
serialization, message flooding, and cancellation races. If an acceptable
isolation boundary cannot be demonstrated in the extension and Android WebView,
defer the module or narrow it to a predefined compute/transform API.

## WebFetch: Remove Friction at the Right Boundary

The current per-origin approval is broader than the threat it is trying to
control. A safer, more useful boundary is based on request capability:

- Safe Reads: public `GET`/`HEAD`, no credentials or sensitive headers, bounded
  response, safe redirects, private-network blocking, and rate limits. No
  per-origin prompt.
- Advanced: broader methods/headers or other future powers. Explicitly enabled
  and separately consented.
- Disabled: no WebFetch.

Even a read-only request can leak information through URL/query parameters, so
the helper/docs should warn scripts not to include adventure data by default and
BetterDungeon should reject known credential fields and credential-bearing URLs.
Removing origin prompts should be paired with a request log and a global kill
switch, not removal of all controls.

## AI Provider Findings

Google documents adjustable safety settings including the sexually explicit
category, alongside non-adjustable core protections. The first step is therefore
to send explicit supported safety settings and run a compatibility matrix. Test
both prompt blocking and output finish reasons; do not infer capability from one
Character Preset failure.

`PROHIBITED_CONTENT` and other block outcomes should map to a stable, visible
Ultrascripts error carrying a safe provider reason. The current design must not
turn an empty candidate set into a silent dropped request.

Google now recommends the Interactions API for new work. `generateContent` is
legacy but still fully supported, so migration is worthwhile without treating it
as an emergency. Begin with independent stateless interactions to preserve the
current public contract. Server-managed continuation IDs introduce retention,
expiry, retry, and adventure-lifecycle questions and should be a later decision.

The proposed model chain uses current model IDs. Verify per-model support for
thinking and structured outputs in the actual migration tests rather than
assuming identical payloads across Gemini and Gemma.

OpenRouter should remain conditional. It adds API-key UX, billing/cost controls,
provider/model selection, privacy disclosures, moderation variance, and a larger
test matrix. If required, introduce a provider adapter first and keep
`ai.status`/`ai.query` provider-neutral for scripts.

## Navigator Product Shape

Navigator's strongest differentiation is adventure upkeep rather than scenario
creation. The initial task set should focus on painful, common maintenance:

- diagnose conflicting or stale Plot Components;
- find bloated, duplicate, or broken-trigger Story Cards;
- rewrite tone/instruction components;
- create or update cards for newly important people, places, and facts;
- summarize recent changes and suggest what is now stale;
- brainstorm without changing anything.

Navigator should use explicit typed tools, never raw unrestricted GraphQL chosen
by the model. A mutation plan should include target stable ID, expected old
version/hash, proposed value, reason, and inverse data. On apply, refetch and
reject or rebase conflicts rather than overwriting newer user changes.

Recommended modes:

- Ask: chat and read-only analysis.
- Suggest: produce a reviewable change set.
- Apply: execute approved changes with audit and undo.
- Automate: run a saved instruction under a fixed trigger and policy.

Avoid starting with a broad autonomous agent. A narrow tool catalog and high
quality context assembly will matter more than an elaborate persona.

## Navigator Automations

Every automation should contain:

- stable id and enabled flag;
- trigger type and trigger configuration;
- instruction and allowed tool scope;
- apply policy: dry run, approval, or automatic;
- cooldown, run cap, and token/request budget;
- last evaluated marker, last successful marker, and pending job id;
- run history with proposed/applied changes and errors.

Start with deterministic triggers (`every N completed turns`, `after Do/Say/Story`)
and define exactly what counts as a turn. Evaluate triggers using monotonically
increasing adventure markers and idempotency keys so reloads and multiple clients
cannot double-run them. Natural-language event triggers can come later.

Automation mutations must use the same preview, validation, conflict, audit, and
undo pipeline as interactive Navigator. Provide a global pause and suppress new
runs while an older run for the same automation is pending.

## Suggested Validation Spikes

1. Cross-device heartbeat: PC → vanilla browser, Mobile → vanilla, abrupt close,
   offline, two BetterDungeon clients, and delayed card writes.
2. Gemini safety: default versus explicit safety settings, adult fictional input,
   adult output, JSON output, Character Presets, and every fallback model.
3. Interactions migration: text, JSON schema, thinking levels, errors, timeout,
   usage metadata, and fallback behavior.
4. JS isolation: hostile-code suite on Chromium, Firefox, and Android WebView.
5. Navigator concurrency: user edits between read/preview/apply, undo after later
   manual edits, reload during apply, and multi-device automation firing.

## Current Recommendations

- Commit to the heartbeat handshake, platform label fix, Audio, WebFetch revision,
  AI modernization, and Navigator.
- Treat JS as provisional until its threat model passes.
- Treat OpenRouter as provisional until Gemini safety testing fails the product need.
- Ship interactive Navigator before automations and require review by default at first.
