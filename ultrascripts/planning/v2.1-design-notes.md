# BetterDungeon V2.1 Investigation and Design Notes

## Purpose

These notes capture the reasoning behind the roadmap and the decisions that
still need a spike or product choice. They are not implementation truth.

## Heartbeat: Durable Discovery Is Not Live Presence

The current heartbeat is a durable Story Card written on adventure entry and
updated as BetterDungeon observes changes. That makes it good at advertising
modules, ops, and versions, but a previous device can leave a valid-looking card
behind. Timestamps and clean-exit invalidation improve diagnostics but cannot
prove liveness after a crash, network loss, tab kill, or switch to a vanilla device.

Selected protocol:

1. Keep heartbeat as the capability advertisement.
2. Add a persistent monotonic `ultrascripts.beat` counter.
3. Advance it on every successful heartbeat write, including after all observed
   adventure action updates rather than only live-count changes.
4. Have helpers compare the beat once from the Input hook and store the result
   for Context and Output.
5. Treat a changed beat as available and an unchanged beat as stale. The first
   valid observation establishes an optimistic baseline.

This deliberately detects disappearance one turn later. That is acceptable
because module operations are already asynchronous: a script may make one call
that receives no response, then see the unchanged heartbeat on the following
turn, abandon the pending work, and return to its fallback path. This avoids
invasive action interception, continuous timers, and a separate ping protocol.

Implementation notes:

- Use a heartbeat revision, not live count, so Retry, undo, and rewind cannot
  confuse the liveness check.
- A heartbeat refresh caused by module enablement/configuration may also advance
  the beat; any recent BetterDungeon write is valid liveness evidence.
- Select duplicate heartbeat candidates by valid protocol and newest beat rather
  than preferring the card with the largest module list.

Platform naming should use `PC` and `Mobile` as the user-facing values. Keep
transport/runtime detail in a separate field so `PC` does not become a proxy for
Chromium versus Firefox.

## Audio Module

The module should remain a small state consumer. A script writes the audio it
wants to `ultrascripts:state:audio`; BetterDungeon reads that state and makes
the browser or WebView match it. The module does not need a request/response
operation protocol for ordinary playback.

Initial shape:

- Focus exclusively on synthesis for one-shot sound effects.
- A synthesized sound includes a changing event id or revision so the same sound
  can intentionally be triggered more than once through state updates.
- Synth requests use bounded notes or frequencies, oscillator types, envelopes,
  duration, volume, and simple sequencing.
- Background music, bundled audio files, and remote audio URLs are unsupported.

Implemented first contract:

- the initial state card represents one optional one-shot effect;
- the module toggle is the initial master stop control;
- leaving the adventure and removing the state card stop playback;
- per-adventure effect ids prevent state hydration from replaying stale sounds;
  and
- the bundled loop experiment was removed because its size, limited range,
  copyright/provenance cost, and redundancy with music services did not justify
  the feature.

Questions remaining after the basic implementation:

- Should script-authored note sequencing be added to the synthesizer?
- Should friendly note names be accepted alongside raw frequencies?
- Is the module toggle sufficient as the V1 master stop, or should Audio receive
  dedicated volume/mute settings before release?

Key pitfalls are browser autoplay rules, mobile background suspension, repeated
state hydration accidentally replaying effects, clipping, and cleanup. The V1
design should solve these directly without introducing channels, a general
mixer, remote URLs, or arbitrary Web Audio graphs.

## JS Module

This is the highest-risk proposed module. A Web Worker improves isolation and
allows hard termination, but `eval` inside a Worker is not by itself a complete
security boundary. The implementation must ensure the worker has no privileged
extension/page references and should assume hostile code.

Recommended V1 contract:

- source string plus JSON input;
- JSON output or structured error;
- no network, storage, DOM, imports, timers, extension APIs, or cross-request globals;
- strict source/input/output limits;
- worker termination on wall-clock timeout;
- one-shot workers initially to eliminate state leakage;
- fixed engine version and no promise of bypassing every AI Dungeon limit.

Before coding, write an escape/abuse suite covering constructor chains, dynamic
code creation, prototype mutation, infinite loops, allocation bombs, oversized
serialization, message flooding, and cancellation races. If an acceptable
isolation boundary cannot be demonstrated in the extension and Android WebView,
defer the module or narrow it to a predefined compute/transform API.

## WebFetch: One Narrow Public-Read Capability

WebFetch 1.0 uses the module toggle as its single control and exposes only
bounded, credential-free public HTTPS reads. It supports `GET` and `HEAD`, no
request bodies, text-like responses, bounded custom headers, safe manual
redirects, private/literal-address blocking, rate limits, and consistent timeout
and body-size limits. The old per-origin approval system and search wrapper are
removed instead of replaced with profiles, Advanced mode, or request history.

Even a read-only request can deliberately transmit information through URL
query parameters or permitted custom headers. Documentation therefore warns
authors not to include sensitive adventure/user data by default. BetterDungeon
prevents ambient credential access, strips sensitive headers, rejects embedded
URL credentials, and avoids logging query strings outside explicit debug mode;
it cannot infer whether author-supplied query data is sensitive.

## AI Provider Findings

Google documents four adjustable safety categories, including sexually explicit
content, and the documented default threshold for Gemini 2.5 and 3 is already
`OFF`. The Interactions API currently does not support custom safety settings,
so BetterDungeon relies on those provider defaults rather than sending an
unsupported field. This does not unlock content rejected by core protections.

The Interactions API reports generation blocks through stable error codes.
BetterDungeon normalizes `safety` to `safety_blocked` with provider reason
`SAFETY`, and `prohibited_content` to the distinct `prohibited_content` error
with provider reason `PROHIBITED_CONTENT`. The latter cannot be treated as a
threshold BetterDungeon can tone down. Google's
current prohibited-use policy also expressly includes sexually explicit content
created for pornography or sexual gratification, so Gemini cannot be assumed to
support BetterDungeon's explicit-fiction use case even when all adjustable
filters are off.

Run a compatibility matrix across the actual fallback models and preserve the
Interactions error code as a safe provider reason. Every block should map to a
stable, visible Ultrascripts error; a response without model-output text must
never become a silent dropped request. If ordinary adult fictional cases return
`PROHIBITED_CONTENT`, treat Gemini as incompatible with that product requirement
rather than attempting to bypass a non-adjustable protection. User testing has
now confirmed that Gemini is not reliable for explicit NSFW scenarios. That is
an accepted Gemini-only limitation for V2.1; reducing setup friction is currently
more important than adding another provider and API-key flow.

Google now recommends the Interactions API for new work. BetterDungeon uses
independent stateless interactions with `store: false`, preserving the current
public contract without server-managed continuation state. Continuation IDs
would introduce retention, expiry, retry, and adventure-lifecycle questions and
remain a later decision.

The model chain is `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`,
`gemma-4-31b-it`, and `gemma-4-26b-a4b-it`. The adapter translates thinking by
model family and uses Interactions `response_format` for schema-backed JSON;
live verification still needs to confirm every fallback model's behavior.

The provider-neutral foundation is complete on PC and Mobile. The executor now
owns a small internal registry/router for status, text/JSON generation,
capability reporting, usage, normalized errors, and consumer-specific provider
resolution. Gemini self-registers as an adapter, while Character Presets and the
Ultrascripts AI module only use the shared executor. Navigator and any future
provider can join the same boundary without adding provider-specific calls to
features.

Gemini remains the only configured provider for V2.1. OpenRouter and local models
remain future candidates because they add key/setup friction, billing and cost
controls, model compatibility, privacy disclosure, moderation variance, and a
larger test matrix. Keep `ai.status`/`ai.query` provider-neutral so evaluating
those options later does not require another feature-level refactor. If another
provider is added, scenario content must never silently fail over to it.

## Navigator Product Shape

Navigator's strongest differentiation is adventure upkeep rather than scenario
creation. The initial task set should focus on painful, common maintenance:

- diagnose conflicting or stale Plot Components;
- find bloated, duplicate, or broken-trigger Story Cards;
- rewrite tone/instruction components;
- create or update cards for newly important people, places, and facts;
- summarize recent changes and suggest what is now stale;
- brainstorm without changing anything.

Navigator should use explicit typed tools, never raw unrestricted GraphQL chosen
by the model. A mutation plan should include target stable ID, expected old
version/hash, proposed value, reason, and inverse data. On apply, refetch and
reject or rebase conflicts rather than overwriting newer user changes.

Recommended modes:

- Ask: chat and read-only analysis.
- Suggest: produce a reviewable change set.
- Apply: execute approved changes with audit and undo.
- Automate: run a saved instruction under a fixed trigger and policy.

Avoid starting with a broad autonomous agent. A narrow tool catalog and high
quality context assembly will matter more than an elaborate persona.

## Navigator Automations

Every automation should contain:

- stable id and enabled flag;
- trigger type and trigger configuration;
- instruction and allowed tool scope;
- apply policy: dry run, approval, or automatic;
- cooldown, run cap, and token/request budget;
- last evaluated marker, last successful marker, and pending job id;
- run history with proposed/applied changes and errors.

Start with deterministic triggers (`every N completed turns`, `after Do/Say/Story`)
and define exactly what counts as a turn. Evaluate triggers using monotonically
increasing adventure markers and idempotency keys so reloads and multiple clients
cannot double-run them. Natural-language event triggers can come later.

Automation mutations must use the same preview, validation, conflict, audit, and
undo pipeline as interactive Navigator. Provide a global pause and suppress new
runs while an older run for the same automation is pending.

## Suggested Validation Spikes

1. Cross-device heartbeat: PC → vanilla browser, Mobile → vanilla, abrupt close,
   offline, two BetterDungeon clients, and delayed card writes.
2. Gemini safety: provider defaults, adult fictional input, adult output, JSON
   output, Character Presets, and every fallback model.
3. Interactions migration: text, JSON schema, thinking levels, errors, timeout,
   usage metadata, and fallback behavior.
4. JS isolation: hostile-code suite on Chromium, Firefox, and Android WebView.
5. Navigator concurrency: user edits between read/preview/apply, undo after later
   manual edits, reload during apply, and multi-device automation firing.

## Current Recommendations

- Commit to the heartbeat beat, platform label fix, Audio, WebFetch revision,
  AI modernization, and Navigator.
- Treat JS as provisional until its threat model passes.
- Keep Gemini as the sole V2.1 provider behind the provider-neutral internal
  adapter and stable public AI contract.
- Ship interactive Navigator before automations and require review by default at first.
