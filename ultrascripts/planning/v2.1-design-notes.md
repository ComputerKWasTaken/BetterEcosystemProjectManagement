# BetterDungeon V2.1 Investigation and Design Notes

## Purpose

These notes capture the reasoning behind the roadmap and the decisions that
still need a spike or product choice. They are not implementation truth.

## Heartbeat: Durable Discovery Is Not Live Presence

The current heartbeat is a durable Story Card written on adventure entry and
updated as BetterDungeon observes changes. That makes it good at advertising
modules, ops, and versions, but a previous device can leave a valid-looking card
behind. Timestamps and clean-exit invalidation improve diagnostics but cannot
prove liveness after a crash, network loss, tab kill, or switch to a vanilla device.

Selected protocol:

1. Keep heartbeat as the capability advertisement.
2. Add a persistent monotonic `ultrascripts.beat` counter.
3. Advance it on every successful heartbeat write, including after all observed
   adventure action updates rather than only live-count changes.
4. Have helpers compare the beat once from the Input hook and store the result
   for Context and Output.
5. Treat a changed beat as available and an unchanged beat as stale. The first
   valid observation establishes an optimistic baseline.

This deliberately detects disappearance one turn later. That is acceptable
because module operations are already asynchronous: a script may make one call
that receives no response, then see the unchanged heartbeat on the following
turn, abandon the pending work, and return to its fallback path. This avoids
invasive action interception, continuous timers, and a separate ping protocol.

Implementation notes:

- Use a heartbeat revision, not live count, so Retry, undo, and rewind cannot
  confuse the liveness check.
- A heartbeat refresh caused by module enablement/configuration may also advance
  the beat; any recent BetterDungeon write is valid liveness evidence.
- Select duplicate heartbeat candidates by valid protocol and newest beat rather
  than preferring the card with the largest module list.

Platform naming should use `PC` and `Mobile` as the user-facing values. Keep
transport/runtime detail in a separate field so `PC` does not become a proxy for
Chromium versus Firefox.

## Audio Module

The module should remain a small state consumer. A script writes the audio it
wants to `ultrascripts:state:audio`; BetterDungeon reads that state and makes
the browser or WebView match it. The module does not need a request/response
operation protocol for ordinary playback.

Initial shape:

- Focus exclusively on synthesis for one-shot sound effects.
- A synthesized sound includes a changing event id or revision so the same sound
  can intentionally be triggered more than once through state updates.
- Synth requests use bounded notes or frequencies, oscillator types, envelopes,
  duration, volume, and simple sequencing.
- Background music, bundled audio files, and remote audio URLs are unsupported.

Implemented first contract:

- the initial state card represents one optional one-shot effect;
- the module toggle is the initial master stop control;
- leaving the adventure and removing the state card stop playback;
- per-adventure effect ids prevent state hydration from replaying stale sounds;
  and
- the bundled loop experiment was removed because its size, limited range,
  copyright/provenance cost, and redundancy with music services did not justify
  the feature.

Possible post-V2.1 enhancements:

- Should script-authored note sequencing be added to the synthesizer?
- Should friendly note names be accepted alongside raw frequencies?
- Is the module toggle sufficient as the V1 master stop, or should Audio receive
  dedicated volume/mute settings before release?

Key pitfalls are browser autoplay rules, mobile background suspension, repeated
state hydration accidentally replaying effects, clipping, and cleanup. The V1
design should solve these directly without introducing channels, a general
mixer, remote URLs, or arbitrary Web Audio graphs.

## Deferred JavaScript Execution Research

Arbitrary JavaScript execution is not part of BetterDungeon V2.1. No current
first-party or showcase script has demonstrated a workload that justifies the
security, platform, package-size, and maintenance cost of a second JavaScript
runtime.

A credible implementation would require an isolated engine such as QuickJS,
strict resource controls, disposable workers, hostile-code coverage, and a
separate safe hosting path for Chromium, Firefox, and Android WebView. QuickJS
would provide a stronger boundary but execute more slowly than native browser
JavaScript. Ultrascripts' bounded Story Card transport would also keep large
inputs and outputs impractical even if the guest received a larger heap and a
longer execution window.

Executing scenario-supplied logic also creates extension distribution and
review risk under Chrome's
[Manifest V3 remotely hosted code requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements).
That concern must be evaluated before any future implementation commitment.

Reconsider this concept only after a real script demonstrates a repeatable task
that cannot fit within AI Dungeon's time or memory limits. Use that task as the
benchmark and requirements source. Prefer a narrow packaged compute operation
shared by multiple scripts before introducing arbitrary source execution.

## WebFetch: One Narrow Public-Read Capability

WebFetch 1.0 uses the module toggle as its single control and exposes only
bounded, credential-free public HTTPS reads. It supports `GET` and `HEAD`, no
request bodies, text-like responses, bounded custom headers, safe manual
redirects, private/literal-address blocking, rate limits, and consistent timeout
and body-size limits. The old per-origin approval system and search wrapper are
removed instead of replaced with profiles, Advanced mode, or request history.

Even a read-only request can deliberately transmit information through URL
query parameters or permitted custom headers. Documentation therefore warns
authors not to include sensitive adventure/user data by default. BetterDungeon
prevents ambient credential access, strips sensitive headers, rejects embedded
URL credentials, and avoids logging query strings outside explicit debug mode;
it cannot infer whether author-supplied query data is sensitive.

## AI Provider Findings

V2.1 ships one provider-neutral executor and one OpenAI-compatible Chat
Completions transport on PC and Mobile. The popup exposes three explicit service
profiles: Gemini, OpenRouter, and a remote Custom HTTPS endpoint. Ultrascripts,
Character Prefill, and Navigator depend on the shared executor rather than a
service-specific implementation.

The public `ai.status`/`ai.query` contract remains provider-neutral. Scripts do
not select services or models and never receive API keys. Successful results may
include diagnostic service, model, fallback, thinking, and usage metadata, but
gameplay logic should not depend on provider-specific values.

Gemini automatic mode uses `gemini-3.5-flash-lite`,
`gemini-3.1-flash-lite`, `gemma-4-31b-it`, and `gemma-4-26b-a4b-it`, stepping
down only after rate limits. Manual Gemini, OpenRouter, and Custom profiles do
not silently change models or services.

All services use normalized errors for missing configuration, authentication,
rate limits, timeouts, safety/content blocks, malformed responses, and transport
failures. Provider restrictions remain provider restrictions; BetterDungeon
surfaces them and lets the player choose another configured service rather than
attempting to bypass them or silently failing over.

## Navigator Product Shape

Navigator's strongest differentiation is adventure upkeep rather than scenario
creation. The initial task set should focus on painful, common maintenance:

- diagnose conflicting or stale Plot Components;
- find bloated, duplicate, or broken-trigger Story Cards;
- rewrite tone/instruction components;
- create or update cards for newly important people, places, and facts;
- summarize recent changes and suggest what is now stale;
- brainstorm without changing anything.

Navigator should use explicit typed tools, never raw unrestricted GraphQL chosen
by the model. A mutation plan should include target stable ID, expected old
version/hash, proposed value, reason, and inverse data. On apply, refetch and
reject or rebase conflicts rather than overwriting newer user changes.

Shipped modes:

- Read-only: chat, analysis, and Story Card research without mutation tools.
- Proposal mode: produce a reviewable change set.
- Apply: execute only after direct player approval, conflict checks, and server
  read-back. V2.1 does not include Undo or a durable mutation audit log.

Avoid starting with a broad autonomous agent. A narrow tool catalog and high
quality context assembly will matter more than an elaborate persona.

Two findings sharpened this shape during architecture work:

- The script-facing `ai.query` contract cannot carry Navigator. It is single-shot,
  capped at 12k characters, and non-streaming. Navigator needs an additive
  first-party chat surface on the same provider registry, leaving `ai.query`
  frozen.
- Grounding must be a hand-written paraphrase of roughly 1k tokens, not an
  injection of the internal documentation corpus. Context cost is a product
  constraint, and a smaller payload also reduces provider content-filter surface.

Delivery order was therefore: first-party chat surface, shell with grounded
read-only chat, read tools, then mutation tools with preview and explicit
confirmation. Those stages, provider setup, and the touch-first Mobile port are
complete.

## Navigator Automations (Cancelled)

Scheduled, event-triggered, and unattended Navigator execution is no longer
planned. Navigator remains player-initiated, proposal-based, and explicitly
confirmed. Automation architecture should not influence V2.1 implementation or
release decisions.

## Suggested Validation Spikes

1. Navigator context: representative adventures with stale, conflicting,
   duplicated, missing, and unusually large Plot Components and Story Cards.
2. Navigator concurrency: user edits between read, preview, and apply, plus
   reload or navigation during apply.
3. Navigator recovery: partial mutation failure, stale identifiers, adventure
   navigation, disabled mutation access, and interrupted AI requests.

## Current Recommendations

- Heartbeat reliability, Audio, WebFetch revision, AI modernization, desktop
  Navigator, and Mobile Navigator are complete.
- Keep arbitrary JavaScript execution deferred until a real workload proves its
  value and a distribution-safe cross-platform boundary is feasible.
- Preserve explicit provider selection, the stable public AI contract, and the
  prohibition on silent cross-provider failover.
- Automations are cancelled, not deferred.
